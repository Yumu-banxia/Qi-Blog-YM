这个博客没有构建步骤

2026-10-11技术选型

  • 技术选型
  • 性能预算
  • 静态站点

仓库里没有 package.json，也没有构建产物目录。提交上去的文件就是浏览器读取的文件，改完之后刷新页面即可看到结果。

本地文件直接打开

作品以压缩包形式提交，评审很可能双击 index.html 查看。这种打开方式下页面处于 file:// 环境，ES module 受跨源策略限制，外部模块与本地数据文件的读取都会失败。因此脚本全部使用 classic script，资源引用一律用相对地址。

构建产物通常以站点根目录为前提，用绝对地址引用样式与脚本，本地文件打开时会全部取不到。这一条直接排除了若干静态站点生成器。

<link rel="stylesheet" href="../assets/styles/tokens.css?v=8">
<link rel="stylesheet" href="../assets/styles/base.css?v=8">
<script src="../assets/scripts/capability.js?v=8"></script>
<script src="../assets/scripts/main.js?v=8" defer></script>

首屏体积

预算定为：HTML 与 CSS 未压缩合计 120 KB 以内，页面自带脚本 40 KB 以内。实施后的实测值是，首页首屏 29.6 KB；文章列表、作品、关于三页在 26.4 KB 到 27.9 KB 之间；文章详情页 47.9 KB，多出来的是文章正文本身。

脚本方面，每页加载的 capability.js 为 5.4 KB、main.js 为 5.1 KB，文章页再加 reader.js 的 14 KB。这些数字按未压缩体积相加，第三方渲染库单列，只在文章页命中内容时进入请求队列。

维护成本

页头与页尾在每一页各存一份，改动一处需要逐页同步，代价与页面数量成正比。约定是页面超过八页时改用一次性生成脚本，脚本只在开发阶段运行，产物仍然是纯静态文件。

一并放弃的还有组件库与原子化样式。按需引入依赖构建阶段完成，无构建方案下要么整份引入，要么自己写。当前样式表 gzip 后约 5.3 KB，而体量最小的通用样式库为 3.6 KB 且组件极少，引入之后还得覆盖默认观感。

代价与边界

没有类型检查，也没有自动化测试；第三方库升级要手动替换本地文件；模板复用依靠复制。项目维持在一位作者、十余个页面的规模时，这些代价可以接受。页面数量或协作人数继续增长时，这套做法的收益会下降，届时应把生成脚本提前到构建阶段。

小结

省掉构建步骤换来的是打开即用与更小的体积，付出的是模板同步与依赖管理上的手工劳动。判断依据是项目规模与交付方式，两边的数字都摆在明处，取舍就清楚了。
